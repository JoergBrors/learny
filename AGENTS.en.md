# AGENTS.md — Guide for AI Assistants and Developers

LearnCards is a flashcard learning platform in C#/.NET 10. Blazor Web App (interactive server rendering), REST API, and OIDC live in `src/LearnCards.Web`; an independent MCP server lives in `src/LearnCards.McpServer`. **Source project convention:** code comments, UI text, and documentation are written in **German**; identifiers in English. This English translation does not change that convention.

## Process for Every Change

1. Find the affected area in the table below and **read its ADR first**, particularly “Guardrails for Changes.”
2. Implement the smallest suitable change using neighboring code as the style example.
3. Build with `dotnet build LearnCards.slnx` (must pass), then run `dotnet run --project tests/LearnCards.IntegrationTests --no-build` (see [docs/testing.en.md](docs/testing.en.md)). Add tests for changes involving users, data, or API. Verify UI with `dotnet run` (see [docs/local-development.en.md](docs/local-development.en.md)) and report what was verified.
4. Update README, docs, Help, and `.env.example` whenever behavior or configuration changes.
5. If a change conflicts with an ADR, never bypass it silently: create a replacement ADR (“Superseded by”) or ask the requester.

## Keep Examples, Templates, Schemas, MCP, and Help in Sync

Every change to card fields, question formats, configuration, or import/export behavior must update **in the same task**: `Api/CardImportSchema.cs` (live schema and example), MCP tool descriptions/schemas (`LearnCards.McpServer/Program.cs`), `wwwroot/templates/*.json`, `demoodule/*.json`, `Help.razor`, and README/docs. The integration suite “Examples, Templates, Schema, MCP, Help” checks all templates and `demoodule/*.json` against live schema, actual import, MCP schema, and Help links. A feature is complete only when docs/examples accurately describe implemented features, never future promises.

## Hard Rules

- **No NuGet packages** unless a new ADR approves them (ADR 0002).
- **Always parameterize SQL.** Queries must run against both SQLite and PostgreSQL (ADR 0004).
- **Image storage (ADRs 0017–0018):** Serve images to clients **only** via `GET /api/images/{id}`, after authorization → cache → storage; never redirect to cloud. Keep metadata in `card_images`, bytes in `IImageStorageProvider`. Generate 32-hex storage keys server-side and validate in every provider. Remote reads use `IStorageAccessBroker` with read-only SAS (`sp=r`, `sr=b`, default 60s) and `StorageUrlGuard`. Never include SAS/signatures/keys in DB, logs, errors, or responses (`SecretRedactor`). Use `SafeHttp` for all outgoing storage requests (no redirect, IP/SSRF checks, size cap). Provider migration is **explicit**, and sources are **never deleted**. No secrets in source.
- **Card images (ADR 0016):** Centralize type/size limits in `CardImageLimits`; every write path runs `CardImageValidator`. Lists return metadata only; omitted `images` retains existing images. Never load arbitrary external URLs or SVG; Base64 never appears in prompts/logs.
- **Blockchain (ADR 0022):** Send transactions only after `AnchorCostGuard` passes with current exchange rate and known gas values (≤EUR 0.001 per credential), plus required mainnet approval. Transaction must use the exact approved gas limit/max fee. Never put private keys into code/DB/logs or personal data on-chain. Keep `UnavailableAnchorSigner` until ADR 0022 item 8 is decided. `QuizService` issues certificates only after verified module quizzes.
- **Rich text (ADR 0020):** Store formatted card text in existing fields as limited markup, **not HTML**. Render only with `RichText.ToHtml` (escaped text, fixed element allowlist); never use `MarkupString` directly with user input. Every write calls `CardJson.Validate`. Editor uses `CardRepository`, `CardImageService`, and `QuizService` rather than creating a separate persistence layer.
- **Quiz (ADR 0019):** One engine for card and module quizzes. Grade only inside `QuizService` using a server-side session; answers must not be sent before submission. Card `quiz[]` is the single source of truth for `card_json` pool projections, updated through `SyncCardQuizAsync` only. Only private-module owners edit config/pool. Generated questions for learners of shared/global modules are ephemeral. Offline fallback must use only allowed question types.
- **Topics (ADR 0027, amended by 0028):** Assign existing modules to topics without duplication; published topic versions and frozen copies (`scope='topic'`) are immutable. Enforce access through `ResolveModuleAccessAsync`/`CanLearnTopicModuleAsync`. Exams use `StartTopicExamSessionAsync` and existing quiz grading, never a second engine. Global versions require admin approval; no topic credentials/blockchain without a new ADR.
- **Topic modules and JSON (ADR 0028):** Drafts contain **owned private modules only**, checked by `TopicService.CanUseModuleInTopicAsync`. Clone global modules first with `ModuleTransferService.CloneGlobalAsync`. Module transfer/cloning use `ModuleTransferService` exclusively with all-or-nothing behavior and no duplicated image/quiz persistence. Topic JSON updates drafts only and never publishes. MCP may manage own drafts/modules but never publish, share, assign, or administer; user tokens may use `POST /api/topics/import` and `PUT /api/topics/{id}/definition` only for topic writes.
- **Topic access and assignments (ADR 0029):** Topic-context access uses `ResolveModuleAccessAsync`/`CanLearnTopicModuleAsync`, only frozen copies, never source private modules. Global, shared, assigned, and mandatory are distinct—**only explicit `mandatory` assignment creates an obligation**. Only `admin` and `themen_admin` may assign/revoke, with DB-backed service authorization, and only to active global, owned, or explicitly shared topics, for a specific version. Auditors/topic admins/admins may view minimized status only (no emails, contents, or answers). Never include `/api/topic-admin/*` in `TokenAllowedPrefixes`, and remove assignment from topic editor.
- **Canonical card JSON is a contract (ADR 0006):** Never rename/remove fields, add only optional ones.
- **AI features preserve offline fallback** (ADR 0008).
- **Private, shared, global modules (ADR 0015):** Private content remains owner-isolated; sharing and admin-approved frozen publication are explicit. Use `ResolveModuleAccessAsync`/`*Readable*` for others' reads and `ownerId` for mutations; **admin does not mean universal private read access**.
- **Multi-user isolation (ADR 0011):** All module/card reads/writes filter on `ownerId` in SQL. User ID comes only from `uid` claim/`HttpContext.Items`, never request data. Use `UserService.RequireRoleAsync` (DB check) for sensitive changes.
- **MCP tokens/clients (ADR 0025):** HMAC all tokens, one-use codes and client secrets with mandatory `MCP_TOKEN_KEY` from `.env` outside DB/backups; protect every row with `row_mac` checked in constant time before authentication. AES-256-GCM for OAuth clients (AAD = `client_id`); never retain partial token hints. Never expose plaintext in DB/logs/audit/responses.
- **MCP card tools (ADR 0007 addendum):** `update_card` exclusively uses `PUT /api/cards/{id}` → `UpdateCardAsync` (no duplicate write logic; private owned cards only, 403/404 otherwise; omitted `images` retains, empty removes; conflicts via `X-Card-Updated-At`). `get_card`/`export_cards` return validated Base64 through `CardImageService`, never storage keys/providers/SAS, batched within `ModuleTransferService.MaxCardBatch`/`CardBatchImageBudgetChars`. Never export owner fields or other users' card IDs.
- **MCP:** All data access uses the user's token (ADR 0013). `MCP_API_KEY` is service-only, grants no user data access, and must never reach clients. Never store/log plaintext tokens/codes.
- Business logic belongs in `Services/`, not `.razor` or endpoint lambdas.
- **Never commit secrets** (`.env`, `mcpsettings.json`, keys). `src/LearnCards.Web/Data/keys/` contains a historically committed Data Protection key—do not extend or reuse it; keys do not belong in the repository.
- **Operating mode (ADR 0026):** Development login is never for production. Outside `Development`, `auto`, typo, or absent OIDC config **fails startup** instead of silently enabling dev. If `ENV_FILE` is set and unreadable, fail startup. Further hardening is proposed in ADR 0014.
- **Do not** create/push Git tags, delete data, or trigger deployments without explicit user instruction.
- `bin/`, `obj/`, `publish-web-test/` are generated build outputs, not source files.
