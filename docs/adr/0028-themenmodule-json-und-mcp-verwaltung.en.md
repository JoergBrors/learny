# 0028 — Owned Topic Modules, Portable JSON Definitions, and MCP Management of Topic Drafts

- **Status:** Accepted (supplemented by [0029](0029-themenzugriff-pflichtzuweisungen-und-themenadministration.en.md); supersedes items 2 and 10 of [0027](0027-themen-lernpfade-versionierung-und-abschlusspruefungen.en.md); all other decisions in ADR 0027 remain valid)
- **Date:** 2026-10-25
- **Motivation:** UI terminology blurred the distinction between modules and topics. Topics could directly reference global originals; modules and topics could not be completely backed up or transferred as JSON; and MCP could only read topics.
- **Related:** ADRs [0002](0002-keine-nuget-pakete.en.md), [0004](0004-datenbank-abstraktion.en.md), [0006](0006-kanonisches-karten-json.en.md), [0007](0007-mcp-server.en.md), [0011](0011-mehrbenutzerarchitektur.en.md), [0013](0013-mcp-benutzergebundene-anmeldung.en.md), [0015](0015-freigaben-globale-lernmodule.en.md), [0016](0016-bilder-in-lernkarten.en.md), [0019](0019-einheitliches-quizsystem.en.md), [0027](0027-themen-lernpfade-versionierung-und-abschlusspruefungen.en.md)

## Decision

1. **Topic drafts may contain only owned private modules.** Enforce this centrally in `TopicService.CanUseModuleInTopicAsync` (single source used by UI, REST, MCP, JSON import, publication). The module must belong to the topic owner, have `scope = 'private'`, and resolve to access context `private`. Reject original global modules, modules shared with the owner, frozen topic copies, other users' modules, and unknown modules. The editor displays only owned modules, but server validation is always required.
2. **Clone global modules into personal modules before using them** (`ModuleTransferService.CloneGlobalAsync`, `POST /api/modules/{id}/clone`, MCP `clone_global_module`). Source must be an **active global module**; foreign private, shared, and owned modules are invalid clone sources. The clone is an independent private object with new IDs owned by the cloning user. Copy name, metadata, cards, order, images, card quizzes (`quiz[]`), quiz configuration, and additional pool questions. Do not copy original ownership, shares, publication status, learning progress, results, certificates, audit or admin metadata. Resolve name collisions as “Name (Copy)”, “Name (Copy 2)”, etc. The original is unchanged.
3. **Cloning and module import use the same pathway:** Clone = export global module definition + import as a new owned module. Apply identical validators everywhere (`CardJson.Validate`, `CardImageValidator`), image storage through `CardImageService` (never bypass provider/image proxy), and quiz synchronization (`quiz[]` in a card is the sole source for `card_json` questions). Operation is **all-or-nothing**: fully validate before the first write; on subsequent errors remove the partial module and images using `DeleteModuleAsync`.
4. **Portable, versioned formats** (fields `format` and `schema_version`, currently 1; reject unknown fields or versions):
   - `learny-module`: `name`, `description`, `icon`, `color`, `cards[]` (canonical card JSON including Base64 `images[]`), `quiz_config`, `pool_questions[]` (only editor/AI pool questions; `quiz[]` questions remain inside cards). Import **always creates a new private module**, never overwrites (name conflict → “Name (Import)”). Never accept IDs, owners, or status from JSON.
   - `learny-topic`: `name`, `description`, `modules[]` (`module_name`, `sort_order`, `exam`, `final_exam_questions`, optional embedded `module`), `exam_config.final_exam`, `topic_questions[]`. Modules use a **stable reference**: `reference_id` in module JSON, `module_ref` in topic JSON. A GUID is unique per owner, allocated on first export, survives renaming; clones receive a new one. `module_name` is only a **display name**. Resolve only against owned modules, first by `module_ref`; when absent (legacy format), by unique name. **Never silently fall back to name** for unknown references; report it, as with missing/global/foreign modules. Reuse embedded module definitions when the user already owns a module with that reference (create/overwrite nothing); otherwise create new private modules. Imported module definitions retain reference IDs only when not already used by that user.
   - Existing card-batch format at `/api/schema/import/cards` remains unchanged and backward compatible. New schemas: `/api/schema/import/module`, `/api/schema/import/topic`; templates: `wwwroot/templates/module-template.json`, `topic-template.json`.
5. **Topic JSON changes drafts only.** It neither contains nor modifies immutable versions, exam attempts, shares, assignments, owner changes, or admin decisions. `POST /api/topics/import` creates a new private draft. `PUT /api/topics/{id}/definition` replaces the draft's name, description, ordered modules, exam configuration, and topic questions, incrementing `draft_revision`. It **never publishes**; new versions require explicit publication per ADR 0027. Invalid requests cause no partial changes: validate and resolve modules first. Application failures restore the prior draft or delete only the newly created topic and embedded modules.
6. **MCP manages only own topic drafts and modules** using REST (no database access, user token required; `MCP_API_KEY` never grants data access). In addition to ADR 0027 read-only tools, add `get_topic_import_schema`, `create_topic`, `import_topic`, `update_topic`, `export_topic`, `get_module_import_schema`, `export_module`, `import_module`, `clone_global_module`. Token writes additionally allow **only** `POST /api/topics/import` and `PUT /api/topics/{id}/definition` (plus already permitted `/api/modules*`). Publication, global submission/approval/rejection, administration, sharing, assignments, progress, exam attempts, user search, and replacing module associations remain blocked. The service alone verifies ownership and roles.
7. **Preserve existing behavior:** Publication, versioning, content-hash reuse of frozen copies, existing-engine exams, shares, assignments, admin approval of global topics, and audit are unchanged. New events: `topic.import`, `topic.definition.update`, `topic.export`, `topic.module.replace-clone`, `module.import`, `module.clone`.
8. **Legacy drafts:** Drafts already referencing global modules are not damaged or silently modified. They remain viewable but show `requires_own_copy` and cannot publish until the association is replaced with an owned clone through `POST /api/topics/{id}/modules/{moduleId}/replace-with-clone` (“Replace with own copy”; owner only, Web/REST). Preserve position, module exam, and manual question distribution. Never alter previously published versions.
9. **Navigation:** Separate “Modules” (`/`, tabs Mine / Shared with me / Global modules) and “Topics” (`/topics`, tabs Mine / Shared with me / Assigned to me / Global topics). Existing URLs remain valid.
10. **Owner scope for references:** Resolve `reference_id`/`module_ref` **only within module ownership** (`FindOwnModuleByReferenceAsync`: owner + reference). Different users may have the same GUID (owner-scoped unique index); it must never grant access to another user's module. Never rescue unknown/foreign references by matching names; return an error.
11. **Limits and concurrency:** Module/topic JSON bodies are limited to **30 MB** (`ApiEndpoints.MaxTransferBodyBytes`, Kestrel default); UI uploads at most 28 MB. Oversize requests return 413 with explanatory text; the server may end the connection early, without creating anything. Card image limits still apply (ADR 0016: up to 5 per card, 2 MiB each). Also limit each definition to 2,000 cards, 5,000 pool questions, 100 modules, and 500 topic questions. Concurrent imports of the same reference are serialized per owner/reference (one new module, remaining requests reuse it, within a process); competing name imports select available names. A reference stays associated with exactly one module.
12. **Atomicity verified:** Fault injection at every write stage (module, card, image, quiz, configuration, topic, association, exam, topic question; `TransferIntegrityUnitTests`) leaves no partial data. Failed topic updates restore the prior draft. Failed imports delete only the newly created fixed-ID topic (never another user's same-named topic) and newly created embedded modules. Topic question ordering uses strictly increasing timestamps.

## Consequences

- New optional `modules.reference_id` column (TEXT NULL, owner-scoped unique index, idempotent SQLite/PostgreSQL migration; existing modules receive references upon first export). No new tables, environment variables, or packages. `TopicService` receives `ModuleTransferService` by constructor injection.
- Module exports include Base64 images and can be large (standard Kestrel request limits remain unchanged).
- Directly adding a global module to a topic is no longer possible; clone it first.
- Imported cards retain `sort_order`; card IDs, timestamps, and progress are not transferred.

## Limitations

- References identify modules within one owner's collection. They work on another installation/account only if the same reference was imported there (module import preserves it when unused), or the definition embeds the module.
- No merge: updates replace the entire draft.
- Embedded modules without references create new modules on every import; matching names alone do not cause reuse.

## Guardrails for Changes

- Any new module-to-topic association must use `CanUseModuleInTopicAsync`.
- Module import/export/cloning must use `ModuleTransferService`; never duplicate card/quiz/image persistence or question sources in exports.
- Topic JSON must never read/write IDs, owners, versions, statuses, shares, assignments, or results; JSON routes never publish.
- Extend token-accessible MCP endpoints only through `TokenMayReadTopics` and verify with tests (`TopicTransferTests`, T130).
- Format changes must increase `schema_version` or remain backward-compatible; update `TransferSchema`, templates, MCP descriptions, `Help.razor`, and documentation together.
- Tests: `TopicTransferTests` (T81–T132), “Examples, templates, schema, MCP, help” consistency tests, and `tests/browser/topics-browser-check.js`.
