# 0028 — Eigene Themenmodule, portable JSON-Definitionen und MCP-Verwaltung von Themenentwürfen

- **Status:** Akzeptiert (ersetzt Punkt 2 und Punkt 10 von [0027](0027-themen-lernpfade-versionierung-und-abschlusspruefungen.md); dessen übrige Entscheidungen gelten unverändert)
- **Datum:** 2026-10-25
- **Anlass:** Module und Themen wurden in der Oberfläche leicht verwechselt; Themen konnten globale Originale direkt verwenden, Module und Themen ließen sich nicht vollständig als JSON sichern oder übertragen, und MCP konnte Themen nur lesen.
- **Bezug:** [0002](0002-keine-nuget-pakete.md), [0004](0004-datenbank-abstraktion.md), [0006](0006-kanonisches-karten-json.md), [0007](0007-mcp-server.md), [0011](0011-mehrbenutzerarchitektur.md), [0013](0013-mcp-benutzergebundene-anmeldung.md), [0015](0015-freigaben-globale-lernmodule.md), [0016](0016-bilder-in-lernkarten.md), [0019](0019-einheitliches-quizsystem.md), [0027](0027-themen-lernpfade-versionierung-und-abschlusspruefungen.md)

## Entscheidung

1. **Themenentwürfe enthalten nur eigene, private Module.** Zentrale Regel in `TopicService.CanUseModuleInTopicAsync` (einzige Stelle, genutzt von UI, REST, MCP, JSON-Import und Veröffentlichung): Das Modul muss dem Themeneigentümer gehören, `scope = 'private'` sein und im Zugriffskontext `private` aufgelöst werden. Abgelehnt werden globale Originale, mit dem Benutzer geteilte Module, eingefrorene Themenkopien, fremde und unbekannte Module. Die Modulauswahl im Editor zeigt ebenfalls nur eigene Module; die serverseitige Prüfung ersetzt das nie.
2. **Globale Module werden vor der Verwendung in ein eigenes Modul geklont** (`ModuleTransferService.CloneGlobalAsync`, `POST /api/modules/{id}/clone`, MCP `clone_global_module`). Quelle ist ausschließlich ein **aktives globales Modul**; fremde private, geteilte und eigene Module sind keine Klonquellen. Der Klon ist ein unabhängiges privates Objekt mit neuen IDs und dem klonenden Benutzer als Eigentümer. Übernommen werden Name, Metadaten, Karten, Reihenfolge, Bilder, Kartenquiz (`quiz[]`), Quizkonfiguration und zusätzliche Pool-Fragen; nicht übernommen werden Eigentümer des Originals, Freigaben, Veröffentlichungsstatus, Lernstände, Ergebnisse, Zertifikate, Audit-/Verwaltungsdaten. Bei Namensgleichheit entsteht „Name (Kopie)“, „Name (Kopie 2)“ …. Das Original bleibt unverändert.
3. **Klonen und Modul-Import sind ein Weg:** Klonen = Export der globalen Moduldefinition + Import als neues eigenes Modul. Dadurch gelten überall dieselben Validatoren (`CardJson.Validate`, `CardImageValidator`), die Bildablage über `CardImageService` (kein Umgehen von Image-Proxy/Provider) und die Quiz-Synchronisation (`quiz[]` der Karte bleibt einzige Quelle für `card_json`-Fragen; keine zweite Wahrheitsquelle). Der Vorgang ist **alles oder nichts**: Eingabe wird vollständig vor dem ersten Schreiben validiert; tritt danach ein Fehler auf, wird das angefangene Modul über `DeleteModuleAsync` samt Bildern wieder entfernt.
4. **Portable, versionierte Formate** (`format` + `schema_version`, derzeit 1; unbekannte Felder und Versionen werden abgelehnt):
   - `learny-module`: `name`, `description`, `icon`, `color`, `cards[]` (kanonisches Karten-JSON inkl. `images[]` mit Base64), `quiz_config`, `pool_questions[]` (nur Editor-/KI-Fragen des Fragenpools; Fragen aus `quiz[]` stehen nur in den Karten). Import legt **immer ein neues** privates Modul an, nie ein Überschreiben (Namensgleichheit → „Name (Import)“); IDs, Besitzer und Status werden nie aus dem JSON übernommen.
   - `learny-topic`: `name`, `description`, `modules[]` (`module_name`, `sort_order`, `exam`, `final_exam_questions`, optional eingebettetes `module`), `exam_config.final_exam`, `topic_questions[]`. Module tragen eine **stabile Referenz** (`reference_id` im Modul-JSON, `module_ref` im Themen-JSON; GUID, je Eigentümer eindeutig, wird beim ersten Export vergeben, überlebt Umbenennen, Klone erhalten eine neue). `module_name` ist nur der **Anzeigename**. Auflösung nur gegen eigene Module: zuerst über `module_ref`; ohne `module_ref` (Altformat) über den eindeutigen Namen; eine unbekannte Referenz wird **nicht** still über den Namen aufgelöst, sondern gemeldet (ebenso fehlende, globale oder fremde Module). Eingebettete Moduldefinitionen werden wiederverwendet, wenn der Benutzer bereits ein Modul mit ihrer Referenz besitzt (nichts wird angelegt oder überschrieben), sonst als neue eigene Module angelegt; ein Modul-Import übernimmt die Referenz nur, wenn der Benutzer sie noch nicht verwendet.
   - Das bestehende Karten-Batch-Format (`/api/schema/import/cards`) bleibt unverändert und rückwärtskompatibel; die Schemas liegen unter `/api/schema/import/module` und `/api/schema/import/topic`, Vorlagen unter `wwwroot/templates/module-template.json` und `topic-template.json`.
5. **Themen-JSON ändert nur den Entwurf.** Es enthält und bewirkt keine unveränderlichen Versionen, Prüfungsversuche, Freigaben, Zuweisungen, Besitzerwechsel oder Administratorentscheidungen. Erstellen (`POST /api/topics/import`) legt einen neuen privaten Entwurf an; Aktualisieren (`PUT /api/topics/{id}/definition`) ersetzt Name, Beschreibung, Module in Reihenfolge, Prüfungskonfiguration und Themenfragen des Entwurfs und erhöht `draft_revision`. Es wird nie veröffentlicht; neue Versionen entstehen nur über die ausdrückliche Veröffentlichung (ADR 0027). Fehler lösen keine Teiländerung aus: Validierung und Modulauflösung laufen vorab, ein Fehler beim Anwenden stellt den vorherigen Entwurf wieder her bzw. entfernt das neu angelegte Thema und seine neu erzeugten eingebetteten Module.
6. **MCP verwaltet nur eigene Themenentwürfe und eigene Module** über die REST-API (keine Datenbankzugriffe, Benutzertoken Pflicht, `MCP_API_KEY` gewährt nie Datenzugriff): `get_topic_import_schema`, `create_topic`, `import_topic`, `update_topic`, `export_topic`, `get_module_import_schema`, `export_module`, `import_module`, `clone_global_module` zusätzlich zu den lesenden Werkzeugen aus ADR 0027. Für Tokens zusätzlich freigegeben sind ausschließlich `POST /api/topics/import` und `PUT /api/topics/{id}/definition` (plus die bereits erlaubten `/api/modules*`-Pfade). Gesperrt bleiben Veröffentlichen, globale Einreichung/Freigabe/Ablehnung, Administration, Freigaben, Zuweisungen, Fortschritt, Versuche, Benutzersuche und das Ersetzen von Modulzuordnungen. Besitz und Rollen prüft ausschließlich der Service.
7. **Bestehendes bleibt erhalten:** Veröffentlichung, Versionierung, Hash-Wiederverwendung eingefrorener Modulkopien, Prüfungen auf der bestehenden Quiz-Engine, Freigaben, Zuweisungen, globale Themenfreigabe durch Administratoren und Audit gelten unverändert. Neue Audit-Ereignisse: `topic.import`, `topic.definition.update`, `topic.export`, `topic.module.replace-clone`, `module.import`, `module.clone`.
8. **Altbestand:** Entwürfe, die bereits ein globales Modul verweisen, werden nicht beschädigt oder geändert. Sie lassen sich weiter ansehen, zeigen aber eine Warnung (`requires_own_copy`) und lassen sich nicht veröffentlichen, bis die Zuordnung über `POST /api/topics/{id}/modules/{moduleId}/replace-with-clone` („Durch eigene Kopie ersetzen“, nur Eigentümer, nur Web/REST) auf einen eigenen Klon umgestellt ist (Position, Modulprüfung und manuelle Verteilung wandern mit). Bereits veröffentlichte Versionen werden nie angefasst.
9. **Navigation:** Die Hauptnavigation trennt „Module“ (`/`, Reiter Meine/Mit mir geteilt/Globale Module) und „Themen“ (`/topics`, Reiter Meine/Mit mir geteilt/Mir zugewiesen/Globale Themen). Bestehende URLs bleiben unverändert.

## Konsequenzen

- Eine neue optionale Spalte `modules.reference_id` (TEXT NULL, Unique-Index je Eigentümer, idempotente Migration auf SQLite und PostgreSQL; bestehende Module erhalten ihre Referenz beim ersten Export); keine neuen Tabellen oder Konfigurationsvariablen, keine neuen Pakete. `TopicService` erhält den neuen `ModuleTransferService` per Konstruktor.
- Der Modulexport enthält Bilder als Base64 und kann groß werden (Kestrel-Standardlimit für Anfragen gilt unverändert).
- Ein bisher möglicher Weg (globales Modul direkt im Thema) entfällt; wer ihn nutzt, klont zuerst.
- Importierte Karten behalten ihre `sort_order`; Karten-IDs, Zeitstempel und Lernstände werden nicht übertragen.

## Grenzen

- Eine Referenz verweist nur auf ein Modul desselben Benutzers; auf einer anderen Installation oder in einem anderen Konto hilft sie nur, wenn das Modul dort mit derselben Referenz importiert wurde (Modul-Import übernimmt sie, solange sie frei ist) oder die Definition eingebettet ist.
- Es gibt keinen Merge: Aktualisieren ersetzt den Entwurf vollständig.
- Eingebettete Module ohne Referenz werden bei jedem Import neu angelegt; Namensgleichheit allein führt nie zur Wiederverwendung.

## Leitplanken für Änderungen

- Neue Wege, Module einem Thema zuzuordnen, müssen `CanUseModuleInTopicAsync` verwenden.
- Import, Export und Klonen von Modulen nur über `ModuleTransferService`; keine zweite Karten-/Quiz-/Bildpersistenz, keine Quiz-Wahrheitsquelle im Export duplizieren.
- Themen-JSON darf nie IDs, Besitzer, Versionen, Status, Freigaben, Zuweisungen oder Ergebnisse lesen oder schreiben; JSON-Pfade veröffentlichen nie.
- MCP-Pfade für Tokens nur in `TokenMayReadTopics` erweitern und im Test (`TopicTransferTests`, T130) absichern.
- Änderungen am Format erhöhen `schema_version` oder bleiben abwärtskompatibel; Schema (`TransferSchema`), Vorlagen, MCP-Beschreibungen, `Help.razor` und Docs im selben Auftrag aktualisieren.
- Tests: `TopicTransferTests` (T81–T132), Vorlagen-/Schema-Prüfung im Block „Beispiele, Templates, Schema, MCP, Hilfe“, `tests/browser/topics-browser-check.js`.
